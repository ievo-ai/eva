## L-2026-07-13-01 — A DoS size-guard that short-circuits a read must propagate an explicit "unscanned" state, not collapse into the "absent" return shape
- **Source**: eva-fix-pr run for ievo-ai/skills#376
- **Signal**: Eva's own REQUEST_CHANGES review flagged that the CWE-400 read-guard fix computed an `oversized`/`manifest_oversized` signal but dropped it before `renderIndexMd()` and `main()`'s manifest — so a plugin whose `hooks.json`/`.mcp.json`/`SKILL.md`/`plugin.json` was padded past the 256 KB cap rendered identically to "no hooks" / `has_hooks:false` instead of "unknown — not scanned". A fail-silent integrity regression (CWE-693) in a *security* index: it hides the exact hook/MCP/broad-grant an attacker would plant, and the review judged it worse than the OOM the guard fixes.
- **Root cause**: when adding a defensive short-circuit that skips reading attacker-controlled input, the implementer reused the function's existing empty/error return shape and treated "skipped read" as equivalent to a genuine "absent/none present". The computed skip signal was never threaded into the downstream consumers that map presence→a security-relevant boolean. In a security context, "not scanned" ≠ "not present"; collapsing them erases the signal.
- **Apply next time**: whenever a size/DoS guard short-circuits a read of security-relevant attacker-controlled data, propagate an explicit "unscanned/unknown" state ALL the way to every downstream rendering AND every persisted boolean (add companion `*_unscanned` fields rather than overloading the existing `has_*` boolean), and add a test asserting the unscanned surface renders distinctly from a genuine absent one. Never let a skipped read reuse the "absent" output shape unmarked.

## L-2026-07-15-01 — Cross-repo build's git `origin` remote can point at the wrong repo even though the checked-out file content is correct
- **Source**: eva-implement run for ievo-ai/skills#387 (cross-repo build)
- **Signal**: `git remote -v` showed `origin` = `https://.../ievo-ai/eva.git` even though the working tree's actual file content matched `$TARGET_REPO` (`ievo-ai/skills`) exactly — AGENTS.md, `plugins/ievo/**`, etc. all present and correct. `git push -u origin HEAD` under that stale remote succeeded silently (GitHub allows pushing a new branch with unrelated history), creating a foreign `eva-impl/*` branch in `ievo-ai/eva` containing `ievo-ai/skills`' entire commit history plus the new commit. `gh` CLI (`GH_TOKEN`) was correctly scoped to `$TARGET_REPO` the whole time — `gh api repos/$TARGET_REPO/contents/...` and `gh issue comment` both worked fine — only the git-level `origin` URL was wrong, so a "gh works against the target repo" check does NOT prove the git remote is also correct.
- **Root cause**: not fully diagnosed (harness/runner detail) — the working directory's file content was swapped to the cross-repo target, but `origin`'s URL was left pointing at the repo the runner job is nominally named after (eva).
- **Apply next time**: before the first `git push` in ANY cross-repo build (`$TARGET_REPO != ievo-ai/eva`), explicitly verify `git remote get-url origin` resolves to `$TARGET_REPO` — do not infer this from file-tree content or from `gh` calls succeeding, since `gh`'s auth is independent of the git remote config. If mismatched, `git remote set-url origin "https://x-access-token:${GH_TOKEN}@github.com/$TARGET_REPO.git"` before pushing — `GH_TOKEN` already carries a correctly-scoped token. If a push already landed on the wrong repo, clean it up immediately via `gh api -X DELETE repos/<wrong-repo>/git/refs/heads/<branch>` (the branches-list API can lag a few seconds after the ref delete — re-check with a short retry before assuming the delete failed).

## L-2026-07-16-01 — A CWE-400 "reject unsafe file type before read" guard can silently swallow an existing test's directory-based failure trap
- **Source**: eva-implement run for ievo-ai/skills#391
- **Signal**: after adding an `isOversized()` guard (lstatSync-based, rejects any non-regular-file — symlink, directory, device, etc. — in addition to oversized regular files) immediately before `readFileSync` in `validate_skills.mjs`/`validate_agents.mjs`, the full local test run failed 2 pre-existing tests. Both used a directory named `SKILL.md`/`.md` to make `readFileSync` throw `EISDIR`, specifically to exercise `main()`'s unrelated `file-unreadable` catch-block. The new guard's `!st.isFile()` check now intercepts a directory earlier than `readFileSync` ever runs, so those two tests got a `file-too-large` violation instead of the expected `file-unreadable` message and failed on the string match.
- **Root cause**: the router's own recommendation (mirroring a related still-open issue, #363) was to broaden the guard from a size-only check (matching the sibling `scan_repo.mjs`'s narrower `statSync`-based `isOversized`) to also reject-by-type via `lstatSync` — closing a real gap (a symlink to a device file can report a misleading size when followed). That broadening was correct, but it was added without first checking whether any *existing* test relied on the exact same underlying condition (not-a-regular-file) as its own failure-injection mechanism. The two pre-existing tests happened to use a directory trap for an unrelated purpose, and the new guard's type check now fires on that same condition first.
- **Apply next time**: before adding a "reject unsafe file types before read" guard (anything checking `isFile()`/`isDirectory()`/`isSymbolicLink()` ahead of a read) to a script with an existing test suite, grep the test file for its current failure-injection mechanisms (directory traps, symlink traps, permission traps) and check whether any of them share the exact condition the new guard now intercepts. If so, swap the trap to a condition the new guard does NOT intercept (e.g. `chmod 000` — permission-denial fails at read time, not at stat time, so it stays orthogonal to a type/size guard) rather than just updating the assertion to match the new message — that keeps the original test's actual target code path (the read-time catch/error-handling branch) genuinely covered instead of accidentally re-testing the new guard twice.

## L-2026-07-18-01 — Hand-rolled regex fixes for security gates need independent review, not just self-written tests

**Source:** ievo-ai/skills#392 (branch `eva-impl/392-block-scalar-frontmatter-bypass`), implement build
**Signal:** `/ievo:deep-review`'s `deep-reviewer` sub-agent, run against my own diff before opening the PR, found that my `BLOCK_SCALAR_RE` regex (closing a YAML block-scalar CI-gate bypass, CWE-20) only matched one of YAML 1.2's two valid chomping/indentation orderings (`|-2` but not `|2-`) — leaving the exact bypass the issue reported reachable via the other ordering. My own hand-written tests all passed (100% coverage, all green) because I only tested the ordering I'd already coded for; I never independently derived the full grammar before writing the regex.
**Root cause:** I anchored the regex on the pattern given in the issue's own "Recommendation" section (`/^[|>][+-]?\d*$/`) without independently verifying it against the actual YAML grammar it's meant to model. Tests written afterward inherited the same blind spot as the regex itself, so they couldn't have caught it — self-authored tests validate that code does what the author intended, not that the author's intent was complete.
**Apply next time:** When a fix is regex/grammar-shaped and security-relevant (a CI gate, a validator, an allow/deny pattern), explicitly enumerate the full grammar/spec — not just the sample an issue happened to give — before finalizing the pattern, and treat an independent review pass (deep-review or otherwise) on exactly this class of change as high-value rather than a formality, since author-written tests share the author's blind spots by construction.

## L-2026-07-18-02 — An issue's own recommended regex fix for a $GITHUB_OUTPUT injection guard was itself line-anchored, not string-anchored, and would not have closed the vulnerability

- **Source**: eva-implement run for ievo-ai/skills#379 (branch `eva-impl/379-github-output-semver-guard`)
- **Signal**: while implementing the issue's literal recommendation — validate `plugin.json`'s attacker-controlled `version` field via `printf '%s' "$new" | grep -qE '^[0-9]+\.[0-9]+\.[0-9]+$'` before writing it to `$GITHUB_OUTPUT` — I manually ran the exact exploit payload from the issue's own exploit chain (`"1.0.0\ninjected=malicious"`) through the guard before trusting it, and it PASSED (was accepted) instead of being rejected. `grep -E '^...$'` anchors `^`/`$` to each LINE of stdin, not to the whole input; a two-line payload whose first line is valid semver satisfies the pattern on that line and `grep -q` returns success. The exact same pattern already existed, unmodified, in this file's pre-existing `workflow_dispatch` branch (which the issue explicitly cited as the guard to "mirror") — so it was independently vulnerable to the same bypass, just gated behind a narrower threat model (an authenticated operator triggering `workflow_dispatch` via the API with a crafted multi-line input).
- **Root cause**: copying an issue's own "Recommendation" section's exact regex/tool invocation without independently re-deriving it against the actual exploit chain in the SAME issue. The issue's author (Eva's own prior vuln-scan run) proposed `grep -qE '^[0-9]+\.[0-9]+\.[0-9]+$'` as the fix, but never verified that pattern against the newline-injection payload that motivated the finding — the recommendation inherited the exact blind spot it was meant to close.
- **Apply next time**: for ANY security-relevant regex/format guard (CI gate, output sanitizer, allow/deny check) — including one pulled verbatim from an issue's own "Recommendation" section — manually run the guard against the literal exploit payload from that issue's "Exploit chain" section before trusting it, not just against the happy-path value. For whole-string validation of a shell variable that may legitimately contain newlines (attacker input, `$(...)` command substitution output), prefer bash's `[[ "$var" =~ ^pattern$ ]]` (anchors to the whole string) over `grep -qE '^pattern$'` piped from `printf`/`echo` (anchors per line) — the two are NOT equivalent despite identical-looking pattern text. This reinforces [[L-2026-07-18-01]] (hand-rolled regex fixes for security gates need independent review) with a sharper, reusable rule: the review must specifically include re-running the ORIGINAL exploit payload, not just a differently-shaped test case.

## L-2026-07-23-02 — A plugin-file PR that omits the mandatory version bump still passes CI: the coupling test catches version DRIFT, not an absent bump

- **Source**: eva-fix-pr run for ievo-ai/skills#414 (branch `eva-impl/372-feedback-title-shell-guard`, cross-repo fix)
- **Signal**: Eva's own REQUEST_CHANGES review on this PR judged the security fix itself correct (`feedback/SKILL.md`'s derived issue title written to a file then passed as a double-quoted `--title "$TITLE"`, neutralizing `$(...)`/backticks/`;`/`&&`) but flagged that the PR shipped WITHOUT the AGENTS.md-mandated in-commit version bump — `marketplace.json` (both version fields), `plugin.json`, `discover.mjs` + `evolution_candidates.mjs` `SCRIPT_VERSION` (0.54.5->0.54.6), the AGENTS.md compliance-ledger header, and a `CHANGELOG.md` entry were all missing. Both product gates (Coverage Gate + Pre-commit Gate) were green, so CI never caught it, and the review noted the original implement run skipped the bump because it was "sandbox-blocked."
- **Root cause**: the `discover.test.mjs` / `evolution_candidates.test.mjs` coupling assertions only check that each script's `SCRIPT_VERSION` EQUALS `plugin.json`'s version — i.e. they detect DRIFT between the version-carrying files, not a version that was simply never bumped. A PR that touches a plugin file (`plugins/ievo/**`, `.claude-plugin/**`) but leaves every version file untouched keeps them all mutually consistent at the old value, so the coupling test passes and the omission is invisible to the merge gate. AGENTS.md documents this exact limitation ("The coupling assertion in `discover.test.mjs` catches drift on the coverage-gate"), but the implementer treated the security fix as the whole task and, blocked or not, never completed the mandatory same-commit bump.
- **Apply next time**: whenever an eva-implement/eva-fix PR modifies ANY file under `plugins/ievo/**` or `.claude-plugin/**` (a plugin-file PR, not an infra/docs-only one — those deliberately do NOT bump), treat the AGENTS.md version bump as a non-optional, same-commit part of the change: bump `marketplace.json` (metadata.version + plugins[0].version), `plugin.json`, and EVERY `plugins/ievo/scripts/*.mjs` `SCRIPT_VERSION` (grep for all of them — see [[L-2026-07-06-01]], the checklist is not exhaustive), update the AGENTS.md compliance-ledger header, and add a reverse-chronological `CHANGELOG.md` entry. Never treat "both gates are green" as evidence the bump was done — the coupling test only flags drift, not an absent bump. And if a sandbox/tooling limitation blocks part of a change, do not silently ship the partial PR: complete it or surface the blocker, because an incomplete-but-internally-consistent PR sails through every gate.

- **Root cause**: the doc check answered "is `status=failure` a valid, documented value?" (yes) instead of "does the documented enum contain the conclusion my target signal carries?" (no — the published enum is completed/action_required/cancelled/failure/neutral/skipped/stale/success/timed_out/in_progress/queued/requested/waiting/pending, with no `startup_failure` member, and the run `status` field has no such value either since `startup_failure` is a *conclusion*). Verifying a parameter's validity and verifying its coverage are different questions, and only the second one can catch a filter that silently excludes the detector's whole reason to exist. A smoke test would not have rescued it either: `status=startup_failure` returns 200 with an empty list rather than 422, so "the request didn't error" would have confirmed a false belief.
- **Apply next time**: when writing a detector, name the exact signal class first (here: `conclusion == "startup_failure"`), then read the filter's documented enum looking for THAT value — a filter that cannot name the target class must be dropped and the match moved client-side onto the field documented to carry it. Treat an undocumented enum value that returns 200-with-empty as unverifiable, never as working. And when the intended signal has no live instance to test against (this repo had zero `startup_failure` runs in its whole history, and four sibling repos had none either), the widest defensible query plus a client-side `select` is the correct shape, because it depends on no unproven filter semantics at all.
- Related: `[[L-2026-07-25-16]]` (grep for consumers of a status before suppressing it — the same "reason about the signal, not the mechanism" failure, one layer up).

## L-2026-07-25-20 — A dedup marker copied from a one-run-per-invocation workflow into a loop goes stale on the second iteration: match the loop's granularity to the key's, or the gate files duplicates and eats its own rate cap
- **Source**: eva-fix-pr run for ievo-ai/eva#274 (branch `eva-impl/261-workflow-integrity-sweep`), round 2
- **Signal**: Eva's own REQUEST_CHANGES review blocked the Workflow Integrity Sweep a second time. Its dedup marker is keyed on `workflow_id`, but the open-issue list backing it (`TRACKED`) was fetched ONCE before the loop and never updated, while the loop iterated over *runs*. Since a parse-broken file re-fails on every later trigger (this file's own header says so), several runs in the 100-run window routinely share one `workflow_id`: iteration 1 files the issue, iteration 2 tests its marker against the now-stale `TRACKED`, sees no match, and files a DUPLICATE — and the 2-issues/24h cap is now spent, silencing a genuinely distinct second breakage. Not hypothetical: a live `actions/runs?branch=main&per_page=100` query on this repo returned 3 failed runs and **all 3 shared one `workflow_id`** — collision is the default case, not an edge case. Reproduced end-to-end before fixing, by extracting the step's `run:` body and executing both the pre-fix and post-fix version against one stubbed `gh` fixture (2 runs of workflow 100 + 1 distinct zero-job workflow 200): pre-fix filed workflow 100 **twice** and then hit `skipped_cap=1` on workflow 200; post-fix inspected 3 workflows, filed each of the 2 real breakages exactly once, `skipped_cap=0`.
- **Root cause**: partial adoption of a sibling workflow's pattern. `eva-ci-failure.yml`'s marker + rate-cap idiom was copied "verbatim" (the PR body says so) from a workflow that handles exactly ONE run per invocation — event-driven, so "fetch state, test, act" is trivially sound. Ported into an N-run loop, the mechanism came across but the invariant that made it sound did not. The same file also carries the fix I skipped: its **newest-run-only supersede policy** (an older failure of a workflow that has since re-run is stale news) is precisely what collapses N runs to one per workflow. I took the dedup half of a two-part pattern and left behind the half that guaranteed one item per key. Second, smaller finding, same shape one layer up: the zero-job fallback exists *because* the path-as-name behaviour is observed-not-contracted, yet it filed its issue under the primary path's title and triage text ("This run's file failed … parse"), asserting the very thing the fallback declines to assume — the detection branch was added, the human-facing strings were not re-derived per branch.
- **Apply next time**: (a) When porting a dedup/rate-cap/idempotency gate out of an event-driven workflow into any loop, ask literally "what does the SECOND iteration see?" before anything else. State read once outside a loop that the loop itself mutates is stale by construction — fix it by collapsing the item list to the key's granularity (`group_by(.key) | map(max_by(.ordering))`, preferred: the loop's invariant becomes structural) or by recording writes in-loop. (b) When you copy a pattern from a sibling file, read the WHOLE mechanism in that file and list which of its guards you are dropping and why — a neighbouring guard 200 lines up (here: supersede) is often the precondition the copied part silently assumes. (c) When adding a fallback detection branch with *weaker* evidence than the primary, re-derive every human-facing string (issue title, triage prose, log line) inside that branch — reporting text written once for the strong-evidence path will overclaim on the weak one. (d) For a shell-in-YAML gate, the distinguishing test is cheap and there is no excuse for skipping it: extract the step's `run:` body (`yaml.safe_load` → write to a file), shadow `gh` with a stub, and run BOTH the old and new body over a fixture that contains ≥2 items sharing the dedup key — the fixture class where correct and broken implementations differ (`[[L-2026-07-25-17]]`'s rule, now applied to a workflow instead of a script).
